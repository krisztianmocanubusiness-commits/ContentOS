# Architecture

How Content OS is put together, and the conventions every page migration
(Content, Dashboard, Calendar, Analytics, Team, Assets, Social Accounts,
Inbox — see `PRODUCT_ROADMAP.md` for the migration log) follows. This is
the first version of this document, written alongside the Inbox
migration; it describes the system as it exists today, not a target
state.

## Stack

- **Next.js** (App Router) — Server Components for reads, Server Actions
  for writes. No client-side data-fetching library (no SWR/React Query);
  client components call Server Actions directly.
- **Prisma** (`@prisma/adapter-pg`) against **Postgres**. Generated client
  lives at `src/generated/prisma/` (gitignored, regenerated by `npx prisma
  generate`).
- **NextAuth** (`src/auth.ts`) for session/credentials auth.
- **Tailwind + shadcn-style components** (`src/components/ui/`) for the
  design system.
- **Vitest** for integration tests (real Postgres, mocked `auth()`/
  `server-only`/`next/cache` — see "Testing" below).

## Request lifecycle

Every workspace-scoped page is a Server Component under
`src/app/(dashboard)/w/[workspaceSlug]/<page>/page.tsx`. Its job is:

1. Resolve `workspaceSlug` from `params` (always a `Promise` — this
   Next.js build treats route params/searchParams as async).
2. Call `requireWorkspaceAccess(slug)` to authenticate and authorize.
3. Fetch initial data through that page's `*-data.ts` module.
4. Pass the data as props into a `"use client"` board component
   (`src/components/<domain>/<domain>-board.tsx`) that owns interaction
   state and calls Server Actions for mutations.

Each page also ships `loading.tsx` (a skeleton matching the real layout)
and `error.tsx` (a client component using Next's error-boundary
convention, with a "Try again" button calling `reset()`).

## Multi-tenancy: `requireWorkspaceAccess`

`src/lib/workspace-access.ts` is the single enforcement point for "can
this caller see/act on this workspace." It:

- Redirects to `/login` if there's no session.
- 404s (not redirects) if the resolved user has no `WorkspaceMembership`
  row for that slug — a guessed/stale slug can't be used to probe which
  workspaces exist.
- Is wrapped in React's `cache()` so multiple Server Components/Actions
  resolving the same slug in one request share a single DB round trip.

Every Server Action re-derives the workspace and role from
`requireWorkspaceAccess(workspaceSlug)` itself — it never trusts a
client-supplied workspace id. Every subsequent query is additionally
scoped by `workspaceId` in its `WHERE` clause (defense in depth: even a
bug in the access check can't leak another tenant's rows if every query
is independently scoped).

## Permissions

`src/lib/permissions.ts` defines a fixed set of `Permission` strings
(`manageTeam`, `manageWorkspace`, `createContent`, `publishContent`,
`approveContent`, `manageSocialAccounts`, `manageMonetization`,
`manageInbox`) and a `PERMISSIONS[role][permission]` matrix across the
seven `TeamRole`s (Owner down to Viewer, each role's grants a subset of
the role above it — enforced by a monotonicity test in
`permissions.test.ts`). `hasPermission(role, permission)` is the single
check every Server Action calls before mutating anything.

On the client, `usePermission(permission)` (a hook over
`WorkspaceContext`'s `currentRole`) and `<PermissionButton permission=…>`
(disables itself and shows a tooltip explaining why, rather than hiding
the control) are the two ways UI reacts to a caller's permissions. Reads
are generally permission-open to any workspace member; only mutations are
gated — e.g. anyone can view the Inbox, but only `manageInbox` roles
(Owner/Admin/Manager) can reply, assign, archive, resolve, or note.

## The `ActionResult<T>` convention

Every Server Action returns `src/lib/action-result.ts`'s
`ActionResult<T>`:

```ts
type ActionResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: string; code: "forbidden" | "not_found" | "invalid" | "conflict" };
```

This is a deliberate choice over throwing: client boards can pattern-match
on `code` to decide toast copy without a try/catch, and a permission
failure or a stale-row conflict is exactly as "expected" a return path as
success. Access-check failures (`requireWorkspaceAccess`'s redirect/404)
are the one exception — those throw/redirect, since they represent "this
request should never have been made," not a recoverable business
outcome.

## Audit logging

`AuditLog` (see `DATABASE.md`) is a single table with one nullable,
`onDelete: SetNull` foreign key column per auditable entity type
(`contentItemId`, `calendarEventId`, `workspaceMembershipId`, `assetId`,
`socialAccountId`, `conversationId`), an `AuditAction` enum value, and a
free-form `metadata Json?` for action-specific detail. Every mutating
Server Action writes its domain row and its audit row in the same
`prisma.$transaction([...])` — either both happen or neither does. The
audit trail is meant to outlive the row it describes (hence `SetNull`,
not `Cascade`); nothing reads it yet beyond the Dashboard's recent-
activity feed, but it exists from the first mutation onward rather than
being bolted on later.

## The provider-agnostic pattern

Two migrations needed to model "a real external integration will plug in
here later, but is simulated today," and converged on the same shape:
model the *data*, not a runtime adapter class, unless there's actual I/O
to abstract.

- **Assets** (real I/O: file bytes) uses a runtime `StorageAdapter`
  interface (`src/lib/storage/`) with a local-disk implementation today
  and an R2-shaped implementation as the drop-in replacement — because
  there's a real operation (read/write bytes) to swap.
- **Social Accounts** and **Inbox** (no bytes, just structured data
  standing in for "whatever a provider's API/webhook would eventually
  send") don't introduce a runtime adapter — there's nothing to swap at
  call time. Instead:
  - `SocialAccount.scopes`/`tokenExpiresAt` are populated with plausible
    simulated values instead of a real OAuth handshake, but the schema
    already matches a real handshake's output.
  - `Conversation.type` (`InboxItemType`: Comment / Direct Message /
    Mention / Notification) is the single discriminator every platform's
    native concept maps onto, so list/filter/thread-view code never
    branches on platform. `externalId` (a future webhook-dedup
    idempotency key) and `metadata Json?` (a free-form bucket for
    whatever a given platform's payload looks like) exist unused today so
    a real integration can populate rows in this same shape later without
    a schema migration.

Both are tracked in `TECH_DEBT.md` as "simulated, not real" — the point
of the pattern is that closing the debt is additive (a new webhook
receiver, a real OAuth callback) rather than a rewrite.

## Cursor-based pagination

Introduced by the Inbox migration (`src/lib/inbox-data.ts`) as this
codebase's first paginated list — every prior "many rows" fetch either
fetched everything (Calendar's full-workspace event list) or took a fixed
top-N with no further pages (Dashboard/Analytics/Social-Accounts
previews). The pattern, for any future list that outgrows "fetch it
all":

- A stable multi-column `orderBy` (`[{updatedAt: "desc"}, {id: "desc"}]`)
  — a single non-unique sort column isn't enough to guarantee a page
  boundary never splits a tie.
- `take: limit + 1` (over-fetch by one row) instead of a separate
  `COUNT`/`hasNextPage` query; slicing off the extra row both trims the
  page and tells you whether there's more.
- The last id of the trimmed page becomes `cursor` for the next call:
  `cursor: { id: cursor }, skip: 1`.
- All filters (search, type, status, etc.) live in the same `WHERE`
  clause Prisma builds for the paginated query — never fetch-then-filter
  in memory once cursoring is involved, since that breaks the "N items
  per page" guarantee.
- A separate, non-paginated `count()` query powers header/summary numbers
  ("N unread · M total") that need to reflect the whole filtered set, not
  just the current page.

## Client boards: no `useEffect` for data fetching

Every board component (`ContentBoard`, `AssetsBoard`,
`SocialAccountsBoard`, `InboxBoard`, …) fetches exclusively from event
handlers — a click, a form submit, a debounced `onChange` — never from a
`useEffect` keyed on state. Two reasons this held up under React's newer
`eslint-plugin-react-hooks` rules (`react-hooks/set-state-in-effect`,
`react-hooks/refs`) during the Inbox migration: it avoids the "effect
that synchronously calls `setState`" anti-pattern outright, and it avoids
needing a `useRef` to smuggle the latest value of some state into an
effect that shouldn't re-run every time that state changes (e.g. Inbox's
search-input debounce is a `setTimeout` started from `onChange`, not an
effect watching a `filters` object). Server state that needs to reflect a
completed mutation is re-fetched explicitly by the handler that performed
the mutation, not synchronized reactively.

## Testing

Integration tests run against a real local Postgres (no mocked Prisma),
with `vi.mock("server-only", () => ({}))`, `vi.mock("next/cache", () =>
({ revalidatePath: vi.fn() }))`, and a mocked `auth()` swapped per-test via
an `actAs(user)` helper. Every `*-actions.test.ts` covers, at minimum: the
permission boundary (a role without the required permission gets
`forbidden`), tenant isolation (acting on another workspace's row gets
`not_found`; a non-member gets a 404 via
`rejects.toMatchObject({ digest: expect.stringContaining("NEXT_HTTP_ERROR_FALLBACK;404") })`),
persistence of the mutation, and that it wrote the expected `AuditLog`
row. Every `*-data.test.ts` covers filtering and tenant isolation for
reads.

## Where things live

```
src/app/(dashboard)/w/[workspaceSlug]/<page>/   Server Component page, loading, error
src/components/<domain>/                        client board + dialogs/sheets for that domain
src/lib/<domain>-data.ts                        read queries (Prisma), "server-only"
src/lib/<domain>-actions.ts                      "use server" mutations, ActionResult<T>
src/lib/<domain>-types.ts                        client-safe shared unions (no Prisma import)
src/lib/workspace-access.ts                      tenant-isolation enforcement point
src/lib/permissions.ts                           role → permission matrix
src/lib/action-result.ts                         ActionResult<T>
prisma/schema.prisma                             see DATABASE.md
prisma/seed.ts                                   demo data for every model
```

See `DATABASE.md` for the schema and `API.md` for the full catalog of
Server Actions and HTTP route handlers.
